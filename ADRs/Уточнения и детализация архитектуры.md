# 1. Общие принципы и инфраструктура

### 1.1. Технологический стек
- Контейнеризация: Все компоненты упакованы в Docker-контейнеры. Это гарантирует изоляцию зависимостей и воспроизводимость окружения на любых стадиях (dev/prod).
- Архитектурный стиль: Микросервисная архитектура. Взаимодействие компонентов осуществляется через четко определенные интерфейсы (API).

### 1.2. Принцип разделения данных (Draft vs Publish)
Архитектура строго разграничивает понятия черновика и публикации:
| Характеристика | Черновик (Draft)                            | Публикация (Publish)                                  |
| -------------- | ------------------------------------------- | ----------------------------------------------------- |
| Сущность       | Изменяемое JSON-состояние страницы          | Неизменяемый снимок (snapshot)                        |
| Формат         | JSON                                        | Статический HTML/CSS/JS                               |
| Хранилище      | База данных (MongoDB)                       | Объектное хранилище (S3)                              |
| Доступ         | Низкая латентность записи (частые операции) | Высокая скорость чтения (через CDN)                   |

*__Важно:__ Одна сущность черновика может породить множество версий публикаций. Публикация - это снимок черновика в некоторый момент времени.*

# 2. Логические компоненты системы

### 2.1. Точка входа (API Gateway)
Центральный шлюз для всех внешних запросов от Frontend.
- Маршрутизация: Направление запросов к внутренним сервисам (Draft Service, Publishing Service).
- Безопасность: Аутентификация и авторизация (валидация JWT-токенов, проверка прав доступа, квот).
- Наблюдаемость: Логирование и сбор метрик входящего трафика.

### 2.2. Клиентская часть (Frontend)
Представляет из себя Single Page Application (SPA). Обеспечивает функционал просмотра публикаций, управления черновиками, визуального редактирования. Связь с бэкендом осуществляется исключительно через API Gateway. Имеется поддержка WebSocket Passthrough для синхронизации состояния в реальном времени.

### 2.3. Бизнес-сервисы
**Draft Service (Управление черновиками)**
Сохранение и версионирование актуального состояния страницы. Данные хранятся в документо-ориентированной БД (MongoDB). Использование S3 нецелесообразно из-за требований к латентности записи. Сервис обеспечивает восстановление сессии. При повторном входе Frontend запрашивает последнюю версию черновика для продолжения работы. Имеет внешний интерфейс через API Gateway (WebSocket) и внутренний - gRPC (для запросов от Publishing Service).

**Publishing Service (Публикация и рендеринг)**
Асинхронная обработка, рендеринг и доставка готовых сайтов.
Процесс публикации можно описать по пунктам:
- Прием запроса от Frontend (через API Gateway с валидацией токена и квот).
- Постановка задачи в очередь (Kafka).
- Воркер забирает задачу и запрашивает актуальный черновик у Draft Service напрямую через gRPC (минуя Gateway).
- Запуск движка рендеринга (трансформация JSON -> HTML/CSS/JS).
- Загрузка артефактов в S3.
- Отправка уведомления клиенту об успехе (через WebSocket Passthrough).

# 3. Вспомогательная инфраструктура
- Kafka: Брокер сообщений. Используется для асинхронной коммуникации и буферизации задач публикации (защита от пиковых нагрузок).
- MongoDB: Основное хранилище для черновиков (гибкая схема, высокая скорость записи).
- S3 + CDN: Хранилище и сеть доставки контента для опубликованных версий сайтов.

# 4. Сценарии доступа
### 4.1. Редактирование
Трафик редакторов проходит через полную цепочку безопасности:
Frontend -> API Gateway -> Бизнес-сервисы -> БД/Очереди.

### 4.2. Публичный доступ (Просмотр)
Трафик конечных пользователей оптимизирован для скорости и отказоустойчивости:
Пользователь → CDN → S3 (Static HTML).

*__Важно:__ Запросы посетителей не проходят через API Gateway и бизнес-логику бэкенда.*

*P.S: Я не стал описывать некоторые вещи, такие как, например, удаление черновиков и публикаций. Я также не считаю, что публикация должна удаляться при удалении черновика. Запрос на ее удаление должен поступать отдельно, если у пользователя есть на то желание.*
