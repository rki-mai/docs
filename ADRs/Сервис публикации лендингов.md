# Сервис публикации лендингов

## Контекст

Сейчас сервис [`wb-landing-builder`](https://github.com/WhatTheMUCK/wb-landing-builder/tree/main/wb-landing-builder) играет роль монолита.
Он умеет и работать с лендингами (получение статуса, изменение), так и с их публикацией. Из-за этого могут возникнуть проблемы с распределением
нагрузки, обработки запросов, так как тяжелые операции, такие как публикация лендинга, происходят в рамках одного HTTP запроса.

## Решение

Предлагается вынести логику, связанную с публикациями, в отдельный сервис - Publish Service. Данный сервис будет отвечать за сборку
лендинга в HTML / CSS / JS файлы (далее статические файлы) и их сохранение в S3 хранилище.

## Команды

Сервис будет поддерживать следующие команды:

- **Создание публикации.** В качестве аргументов команды на вход приходит структура лендинга.
  При выполнении команды сервис собирает лендинг и сохраняет результат в хранилище.
  В результате выполнения команды создается новая сущность публикации.

- **Удаление публикации.** В качестве аргументов команды на вход приходит ID созданной публикации.
  При выполнении команды удаляется публикация, соответствующая ID, если она существует.

## Сущности

Сервис оперирует со следующими сущностями

### Публикация

Описывает опубликованный лендинг:

- `id` - идентификатор публикации. Должен быть уникальным среди всех существующих публикаций.
- `assets_path` - URI на статические файлы в S3 хранилище.

## Протокол взаимодействия

Сервис будет принимать команды по протоколу HTTP. Данные будут представлены в формате JSON. Сервис будет поддерживать следующие ручки:

- `[POST] /api/publications` - создание публикации. На вход приходит структура лендинга. Возвращает ID созданной публикации.
- `[GET] /api/publications/:id` - получение состояния публикации. На вход приходит ID публикации. Возвращает [[#Публикация|информацию о публикации]].
- `[DELETE] /api/publications/:id` - удаление публикации. На вход приходит ID публикации.

### Общение со стороны Landing Service

Теперь Landing Service внутри состояния лендинга будет хранить вместо поля `published` поле `publicationId`, которое может отсутствовать.

При обработке команды `/landings/:id/publish` происходит следующий набор действий:

- Landing Service отправляет в Publish Service запрос на создание публикации.
- Publish Service возвращает ID созданной публикации.
- Landing Service создает внутри себя поле `publicationId`, куда записывает ID созданной публикации.

При обработке команды `/landings/:id` происходит следующий набор действий:

- Как и раньше, получаем состояние лендинга из MongoDB
- Проводим постпроцессинг, определяя поля `published` и `publicUrl`

При обработке команды `/landings/:id/unpublish` происходит следующий набор действий:

- Проверяем, что в записи лендинга есть поле `publicationId`
- Если оно есть - отправляет запрос в Publish Service на удаление публикации
- Удаляем запись `publicationId`

При выполнении команды `/public/:id` теперь происходит следующий набор действий:

- Landing Service получает запись лендинга
- Далее смотрим в `publicationId`, и по нему отправляем запрос в Publish Service на получение информации о публикации
- Из информации о публикации узнаем URI на статический файлы в S3 хранилище
- Получаем файл из S3 хранилища и возвращаем его содержимое в качестве ответа
